# 全剧架构与连载记忆

先立骨再写肉。在写任何一集之前，把全剧不可变的事实和分集弧线定下来；每集写完再核对有没有违背。

## 何时使用

- 用户说「这部剧讲的是……」「主角是……」「结局要……」等全剧设定时。
- 要新写、重写某一集，或分集变多后担心人设漂移、伏笔遗忘时。
- 用户问「第几集埋的伏笔回收了吗」「反派到第几集才出场」时。

## 工具调用步骤

1. 先用 `get_current_project` 读取当前剧的标题、风格、已有分集、人物、场景和可用方法；确认用户说的是当前打开的剧。
2. 用 `get_series_notes` 读取全剧笔记。若 `revision` 为 0，说明还没有笔记；这一步不是失败。
3. 和用户一起把信息整理成文档（字段定义见 `references/series-bible-fields.md`）。**不要替用户决定题材、画风、爽点**；用户没说的留空并标注「待定」。
4. 用 `save_series_notes` 保存，带上读到的 `expected_revision`。若返回 `conflict`，重新读取、合并用户的新意图后再存，不要直接覆盖。
5. 用户写集或修改剧本后，调用 `check_series_continuity` 做机械核对。把 `violations` 按「哪条事实、剧本里缺了什么」报给用户，让用户决定改剧本还是改事实。

## 笔记文档的形状

推荐字段（全部可选，缺省视为待定）：

- `premise`：一句话故事。
- `invariants`：跨集不可变事实数组，每项含 `id`、`statement`、`tokens`（用于机械核对的关键词/别名）。
- `relationships`：人物关系与反派层级。
- `arcs`：分集冲突弧线，每集含 `episode`、`conflict`、`turn`、`hook`。
- `payoffs`：伏笔表，每项含 `id`、`planted_at`、`recalled_at`、`status`。

`invariants` 的 `tokens` 是 `check_series_continuity` 唯一会核对的东西：它只做字符串包含检查，不做语义理解。谁的名字、物件名、地点名可能换说法，就都写进 `tokens`。

## 证据与失败处理

- 每次保存后向用户报告 `revision` 和保存了哪些字段。
- `not_found`：当前剧不存在或集数归属不对，停止操作，让用户先打开正确的剧。
- `invalid_kind` / `invalid_document`：工具调用参数不对，修正后重试一次，仍失败就向用户说明。
- `conflict`：笔记已被别处更新。重新读取，展示差异，让用户决定保留哪一版。
- `corrupt_note`：笔记文件损坏。不要自动删除；告诉用户证据已损坏，询问是否从用户口述重建。

## 作者确认门槛

- 只有用户明确说「记下来」「就这么定」时才 `save_series_notes`。
- 工具返回 `conflict` 时，即使你觉得自己能合并，也要把差异给用户看，不擅自选一边。
- `check_series_continuity` 只报机械核对结果，不自动改剧本。它说「没提到」不等于作者真的忘了；让用户判断。

## 能力边界

- 没有写剧本文本或生成分镜的工具。要写集请用现有剧本工具；要拆镜请用分镜工具。
- 不新建数据库表，不写 `dramas.metadata.creative_direction`，不覆盖作者锁定的项目事实。
- `check_series_continuity` 只查 `tokens` 是否在剧本文本中出现，不判断剧情是否真正自洽。语义级问题只能靠用户读完后的判断。
